# Managed files integration

Status: implemented private boundary; integration owner runs shared verification. This is not a full filesystem or product parity claim.

`core/app/src/files` retains the capability filesystem for directory and file admission, bounded reads, create-only staged publication and durable directory park receipts. Portable names reject traversal and cross-platform aliases. Persisted receipts are identity comparisons, never authority to reopen caller-selected paths. Native unresolved outcomes retain the generation needed for settlement.

The retained Minecraft adapter accepts an already admitted `Directory`; it does not acquire a competing physical root lease. Each issued operation, cloned operation and escaped witness retains its original generation. The lifecycle caches the native root so operations on one physical application root share its existing publication coordination. Native directory projections derive retained parent bindings and validate the resulting path; returned paths grant no mutation authority.

Focused checks in `files::tests` cover directory replacement, exact read projection, park-receipt roundtrip and malformed Unicode, and rejecting a second stage write after an empty first payload. The parser uses byte slices so malformed receipt input cannot split UTF-8. A separate writer-admission bit prevents failed or empty writes from allowing a second truncating writer.

Requested integration commands: `cargo test -p axial-app files::tests` and the retained filesystem/Minecraft checks appropriate to `Directory::project_from` and the managed root bridge. Shared Cargo writes belong to the integration owner. Broader native race and platform evidence remains required by the delivery plan.

Generated native extraction receipts now expose idempotent `settle(&self)` after process and output drainage. Cleanup validates the entire original file inventory before any effect, removes exact guarded files through retained native park/removal, then removes only the exact empty owned directory. Failures retain progress and effects in the receipt; replacements and added user files are preserved. Native tests cover successful repeated settlement and replacement refusal.

`publish_native_directory` returns `ManagedNativePublicationFailure` instead of discarding post-creation authority in an I/O error. Its partial receipt is created immediately after the exact directory handle exists, retains earlier files and any final guard returned by a failed per-file publication, and stays with the accepted launch preparation until cleanup settles. An injected second-file post-promotion failure verifies that both promoted files remain owned and can be removed before the manifest exists. A published file whose exact guard cannot be recovered remains ambiguous; matching bytes do not authorize adoption. Process-crash leftovers still need bounded restart-recovery coverage.

## Portable transfer staging

The retained anonymous transient implementation was Linux-only; macOS and Windows returned `Unsupported` before a managed transfer could read its source. Non-Linux targets now keep the same `TransientDestination`/stage/publication API but use the existing capability-owned named `StagedFile`, no-replace promotion receipt, and retained create/discard/promotion obligations. Linux retains its anonymous-file implementation. No caller-authored path, direct temporary-file rename, payload-sized buffer, or larger State-file recovery limit was introduced.

Named writes append through the original admitted handle. Sealing reads that same handle back in 64 KiB chunks, compares SHA-256 against the actual streamed writes, and retains the sealed revision through reads and publication. Destination reservations remain owned until exact publication or cancellation; only the matching registered StageToken can use its own transient reservation. Partial batches retain every member in order. Dropped ambiguous cleanup retains both owners and fences root retirement until exact reconciliation succeeds.

A named member requires two live effect records, so named batches are limited to 256 while Linux remains at 512; the shared 512-effect safety bound is unchanged. The content owner uses matching platform-specific staging windows. The integration owner's strict macOS run passed all seven new tests in `portable-transient-tests-2.log`: 17 MiB multi-frame publication/read/seek with the same file identity, byte drift before seal, revision drift after seal, ordered partial publication with an external collision, dropped cleanup blocked by a replacement, 513 members over bounded windows, and process exit before publication.

Crash cleanup is not equivalent to Linux anonymous staging: named scratch files survive a process exit and are preserved on reopen. The crash test proves that neither an unclaimed scratch file nor a user file with the same prefix is adopted or deleted. Bounded durable restart cleanup remains an explicit gap. Windows compile/runtime evidence, a fresh Linux run, and downstream full transfer journeys remain separate acceptance work; macOS filesystem tests alone do not establish product parity.
